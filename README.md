# 草綠同色 (초록동색)

방치형 수련 + 미니게임 학원물 웹 게임. (구 '국립 창록고등학교')

```bash
npm install
npm run build    # 배포 빌드 (dist/)
npm start        # 서버 실행: 게임 + 채팅 · 파티 · 랭킹  → http://localhost:8787
```

개발 중에는 터미널 두 개로 `npm run server` 와 `npm run dev` 를 함께 띄운다. (vite 가 `/api` 를 8787 로 넘겨 준다.)
서버 없이 `npm run dev` 만 켜도 게임은 돌아가지만 채팅 · 랭킹은 '서버에 연결되지 않음' 으로 표시된다.

환경 변수: `PORT`(기본 8787), `CHOROK_DATA`(랭킹 저장 파일, 기본 `server/data.json`), `CHOROK_DIST`(정적 파일 폴더), `DATABASE_URL`(Supabase 연결 주소. 있으면 랭킹 · 벼룩시장 · 인적사항 카드 · 회원 명부를 DB 에 저장하고, 없으면 `data.json` 에 저장한다. Render 배포에서는 반드시 넣을 것).

### 서버 (`server/index.js`, 의존성 없음)
- 채팅: 연락(RP, 공개) · 담화(일반, 공개) · 일행(파티원끼리만). 최근 100줄을 메모리에 보관한다.
- 파티: 접속자 목록에서 초대 → 상대에게 "일행으로 참여하시겠습니까?" (네/아니오).
- 랭킹: 과목별 각자의 최고 기록만 남기며 `data.json` 에 저장된다.
- 계정 · 캐릭터 저장: 서버(`server/accounts.js`)가 원본을 갖고, 브라우저(localStorage)에는 사본을 둔다. 어느 기기에서든 같은 계정으로 이어서 할 수 있다.
  - 로그인 · 가입은 서버가 확인한다(비밀번호는 scrypt). 로그인하면 토큰(180일)을 받고, 게임 저장은 몇 초씩 모아 `/api/account/save` 로 보낸다.
  - 자동 이전: 서버에 계정이 없고 브라우저에 옛 기록이 있으면, 로그인할 때 비밀번호를 확인해 서버로 옮긴다. 서버 저장 전부터 로그인해 있던 브라우저는 한 번 다시 로그인하게 한다.
  - 두 기기에서 동시에 하면: 서버가 매긴 저장 번호로 판단해, 다른 기기가 먼저 저장했으면 덮어쓰지 않고 그 기록으로 게임을 다시 연다.
  - 서버에 연결할 수 없으면(서버 없이 `npm run dev` 등) 예전처럼 브라우저 안에서만 동작하고, 나중에 서버가 있을 때 로그인하면 옮겨진다.
  - 저장 위치: `DATABASE_URL` 이 있으면 Supabase 의 `saves` 테이블(`account:<아이디>` 줄), 없으면 `server/accounts.json`(`CHOROK_ACCOUNTS` 로 변경).
  - 점수 · 저장 내용은 여전히 브라우저가 보낸 값을 믿는다. (조작 방지는 하지 않는다)

## 구성
- `src/components/Intro.jsx`, `FitLines.jsx` — 첫 캐릭터 생성 전 인트로. 문장 하나는 항상 한 줄이며 화면 폭에 맞춰 글자 크기가 자동 조절된다. 문단 내용은 `src/game/intro.js`

- `src/game/sfx.js` — 효과음. 외부 음원 파일 없이 Web Audio 로 합성한다. 전체 볼륨은 `MASTER` 한 곳에서 조절. 버튼에 `data-sfx="none"` 을 달면 공통 클릭음이 꺼지고, `data-sfx="이름"` 으로 다른 소리를 줄 수 있다
- `src/components/GameModal.jsx` — 과목 → 미니게임 연결표(`MINIGAMES`). 새 게임은 여기에 등록
- `src/components/minigames/` — 미니게임 화면
- `src/game/minigames/` — 규칙·데이터 (UI 없이 테스트 가능)

  - 랭킹은 `server/data.json`. 새 버전을 풀 때 **폴더를 새로 만들지 말고 기존 폴더에 덮어 풀기** (`tar xzf 새파일 --strip-components=1`). `node_modules`와 `data.json`은 안 건드린다.

## v45 (v44 기준) — 진짜 원인 수정
- v44에서 404→400으로 바꾼 건 증상을 드러낸 것뿐, 진짜 원인은 따로 있었다: 한글은 **완성형(NFC)과 조합형(NFD)** 두 가지 유니코드 표현이 있고 화면엔 완전히 똑같이 보인다. 기기·브라우저에 따라 입력이 둘 중 하나로 들어올 수 있는데, 계정은 가입할 때 들어온 그 형태 그대로 저장돼 있었다. 그래서 가입할 때와 다른 형태로 아이디를 치면(예: 관리자가 완성형으로 입력했는데 그 계정이 조합형으로 저장돼 있으면) 서버 입장에서는 다른 문자열이라 "계정이 없다"고 나왔다. ("이요"가 바로 이 경우였다.)
- 이제 아이디가 들어오는 모든 곳(가입·로그인·관리자 비밀번호 재설정 등)에서 완성형(NFC)으로 맞춘다. 이미 조합형으로 저장된 옛 계정도, 조회할 때 완성형으로 못 찾으면 조합형으로 한 번 더 찾아보고, 찾으면 그 자리에서 완성형으로 정리해 둔다(다음부터는 바로 찾는다).
- 테스트로 조합형(NFD)으로 가입한 계정을 완성형(NFC) 아이디로 비밀번호 재설정해 실제로 되는지 확인했다.

## v48_a (v47 기준) — 서버 안정성 · 루미큐브 버그 수정
- **SSE ping 예외 처리**: `server/index.js`의 접속 유지용 ping(`setInterval(() => res.write(': ping\n\n'), 20_000)`)이 try/catch 없이 떠 있어서, 이미 끊긴 연결(close 이벤트가 아직 안 왔을 때)에 쓰다가 예외가 나면 **서버 프로세스 전체가 죽는다 → Render가 재시작 → 그 사이 접속자 전원이 끊겼다 재접속** 하는 현상으로 이어질 수 있었다. 여러 명이 동시에 접속해 있을 때 "연결이 계속 반복적으로 끊겼다 됐다" 하는 증상의 유력한 원인이었다. ping을 try/catch로 감싸고, 혹시 모를 다른 곳의 예외로도 서버 전체가 죽지 않도록 `process.on('uncaughtException'/'unhandledRejection', ...)` 안전망도 추가했다.
- **루미큐브 "턴 마치기"가 제출 후 영영 안 눌리던 버그 수정**: "손댔는지(touched)" 여부를 내 작업대의 조합 id와 서버가 보낸 조합 id를 비교해서 판단했는데, 서버는 `/api/rummi/commit`이 성공할 때마다 **내용이 그대로인 조합까지 포함해 모든 조합 id를 새로 발급**한다. 그래서 "제출하기"가 성공한 직후에도 "아직 안 건드린 상태"로 돌아오지 못하고 "턴 마치기"가 계속 비활성 상태로 남아, 그 사람의 턴이 영원히 안 넘어가는 버그였다(`components/locations/RummikubGame.jsx`). id 비교 대신 명시적인 `touched` 상태값으로 바꿔서(조합을 건드리는 동작에서 `true`로, 되돌리기·턴 시작·제출 성공 시 `false`로) 고쳤다. `t_v47_rummi.mjs`에 제출 뒤 "턴 마치기"가 다시 눌리는지, 실제로 턴이 상대에게 넘어가는지 확인하는 검증을 추가해 재발을 막았다.
- **루미큐브 자잘한 수정 네 가지**(모두 `components/locations/RummikubGame.jsx`):
  - 조커를 조합에 넣을 때, 색·숫자를 고르지 않으면 묵묵히 "빨강 1"로 떨어지던 걸 고쳤다 — 이제 조커가 섞인 채로 "새 조합으로 묶기"/"조합에 추가"를 누르면 "조커로 쓸 색과 숫자를 먼저 골라야 한다"는 안내만 뜨고 막아 둔다(이미 테이블에서 꺼내 와서 전에 쓰던 값이 있는 조커는 그 값을 그대로 이어받은 걸로 쳐서 다시 고르라고 하지 않는다).
  - 테이블의 조합(그룹·런)이 아무 순서 없이 뒤죽박죽 보이던 걸, 그룹은 색 순서로·런은 숫자 오름차순으로 자동 정렬해서 보여 주게 했다(`sortMeldTiles`). 실제로 내는 순서·서버에 보내는 내용은 그대로이고, 보기 좋게 줄만 세운다.
  - 손패 위에 "손패 정렬" 버튼을 새로 달았다(`autoSortHand`) — 이미 3장 이상으로 완성되는 조합(런 먼저, 그다음 그룹)을 욕심쟁이 방식으로 찾아 앞으로 모아 주고, 나머지는 숫자(→색) 오름차순으로 정렬한다. 조커는 엉뚱한 값으로 자동으로 끼워 맞추지 않고 맨 뒤에 그대로 둔다.
  - "조합에 추가하기"·조커 색/숫자 선택 드롭다운 3개에 글자·배경색 클래스가 아예 빠져 있어서, 펼쳤을 때 옵션 글자가 흰 배경에 거의 안 보이던 것을 고쳤다(다른 곳의 드롭다운처럼 `bg-shade`/`text-paper` 클래스를 줬다).
  - 조커는 색·숫자가 정해진 뒤에도 보통 타일과 구별이 안 갔는데, 타일 오른쪽 위에 작은 ★ 표시를 항상 붙여서 한눈에 "이건 조커다"를 알 수 있게 했다(숫자/색이 정해지지 않은 손패의 조커는 전처럼 ★만 크게 보인다).

## v59.1 (v59 기준) — 인적사항 카드 저장을 사람별로 분리 (egress 폭증 수정)
- **문제**: 인적사항 카드(프로필 사진 포함)가 Supabase에 "전원분 한 덩어리"로 저장되고 있었다. 그 결과 단 한 명이 사진을 올리거나 바꿀 때마다, 그때까지 쌓인 **모든 사람의 사진을 포함한 카드 전체**를 매번 다시 Supabase로 내보내고 있었다. v59의 "카드 저장 주기를 느긋하게" 수정은 저장 *빈도*는 줄였지만, 한 번 저장할 때 내보내는 *양*은 그대로였다 — 실사용(동시접속 3명)에서 프로필 사진을 몇 번 바꾸는 것만으로 Supabase 무료 egress 한도(5GB)를 훌쩍 넘기는 원인이 됐다.
- **수정**: 인적사항 카드를 사람별로 한 줄씩(`card:<id>`) 저장하도록 바꿨다. 이제 한 명이 카드(사진)를 고치면 **그 사람 줄만** 다시 쓰고, 다른 사람 사진은 전혀 건드리지 않는다.
- **마이그레이션**: 서버가 처음 뜰 때 예전 방식("전원분 한 덩어리")으로 저장된 카드가 남아 있으면, 자동으로 사람별 방식으로 한 번 옮기고 예전 줄은 지운다. 플레이어가 따로 할 일은 없다.
- 로컬 파일 모드(`data.json`/`cards.json`, DB 미연결)는 트래픽 비용이 없는 환경이라 그대로 한 덩어리로 저장한다 — 이 수정은 Supabase/Postgres 연결 시에만 적용된다.

## v59.2 (v59.1 기준) — 계정 프로필 사진을 자동저장에서 분리 (egress 폭증의 더 큰 원인 수정)
- **문제**: v59.1(인적사항 카드)과는 별개로, **계정 자체의 프로필 사진**(`server/accounts.js`)이 더 큰 원인이었다. 게임은 로그인한 상태에서 약 4초마다 전체 진행 상황을 서버에 저장하는데(`/api/account/save`), 그때마다 계정 레코드 전체(사진 바이트 포함)를 매번 통째로 Supabase에 다시 썼다 — 브라우저가 "사진 안 바뀜" 표시만 보내도, 서버가 그 표시를 보고 **실제 사진 바이트를 다시 채워 넣은 뒤** 그대로 다시 저장하고 있었기 때문이다. 즉, 아무도 사진을 바꾸지 않아도 사진이 이미 설정된 사람은 평소 플레이만으로 몇 초마다 그 사진 전체가 Supabase로 다시 나갔다 — 테스터 3명이 짧은 시간에 쓴 대역폭(약 0.5GB)이 설명되는 가장 그럴듯한 경로다.
- **수정**: 계정 레코드 안에는 사진의 **해시(내용 지문)**만 남기고, 실제 사진 바이트는 따로 떨어진 전용 줄(`avatar:<아이디>:main`, 다중 프로필 계정은 `avatar:<아이디>:p:<프로필id>`)에만 둔다. 저장할 때마다 들어온 사진의 해시를 지금 저장된 해시와 비교해서, **내용이 실제로 달라졌을 때만** 전용 줄에 다시 쓴다 — 사진이 안 바뀐 채로 계속 플레이하면(브라우저가 "안 바뀜" 표시를 보내든, 새로고침 등으로 실제 바이트를 다시 보내든 상관없이) 사진 바이트는 전혀 다시 나가지 않는다.
- 로그인 화면·내 정보 조회처럼 실제 사진이 꼭 필요한 곳(`/api/account/me`, 로그인 응답, 저장 충돌(409) 응답)만 전용 줄을 읽어 실제 바이트를 채워서 돌려주고, 그 외(평소 자동저장)에는 사진 줄을 아예 읽지 않는다.
- **마이그레이션**: 따로 할 일 없음 — 예전 방식(계정 레코드 안에 사진이 그대로 있는 계정)은 다음 저장 때 자동으로 새 방식(해시 + 전용 줄)으로 넘어간다.
- 로컬 파일 모드(DB 미연결)는 트래픽 비용이 없는 환경이라 그대로 계정 레코드에 사진을 둔다 — 이 수정도 Supabase/Postgres 연결 시에만 적용된다.
- 디스크에 직접 만든 모의(mock) `pg` 모듈로 시나리오(최초 업로드/연속 자동저장/새로고침 뒤 재전송/실제 변경/다중 프로필)를 모두 검증한 뒤 테스트 코드는 지웠다.

영능력이 직접 공격력을 산출하는 경우는 [원숭이 손]과 [도깨비불] 두 가지인데, 이전에는 아이템 버프(마이쮸·폭죽)·효험·악기 중 일부가 적용되지 않거나 아예 잘못 계산되고 있었다. 다인/1인 전투 모두 고쳤다.
- **[원숭이 손]**: 효험을 걸고 쓸 수 있게 됐다(`src/game/battle.js`의 `psychicTurn`, `id === 'monkey-paw'`) — 효험이 걸려 있으면 공격 굴림을 두 번 해서 더 나은 쪽을 쓰고, 의지력 10(모자라면 0까지)을 추가로 쓴다. 아이템 버프(마이쮸·폭죽)는 이미 적용되고 있었지만, 쓰고 나서 버프를 꺼 주지 않아 다음 행동에도 또 적용되는 버그가 있어서 함께 고쳤다(`boostUsed` 반환 추가).
- **[도깨비불]**: 아이템 버프 배율이 숫자가 아니라 그냥 "있으면 ×2"로 고정되어 있던 버그를 고쳤다(`fireTurn`의 `mult` 계산) — 이제 마이쮸든 폭죽이든 실제 배율이 그대로 적용된다. 다인 전투에서는 악기(무구 버프)로 쌓이는 일행 전체의 `aura`도 터지는 순간(`fireTurn`)에 빠져 있었는데, 이제 캐스팅한 턴이 아니라 **실제로 터지는 순간의 일행 구성**을 기준으로 계산해서 더한다(`src/game/mbattle.js`의 `resolveTurn`). 효험은 쓰는 시점(기를 모으기 시작할 때)에 걸어 두면, 실제로 터지는 순간(몇 턴 뒤)까지 유지되다가 그때 적용된다 — 새 상태 필드 `fireBuffed`로 들고 있는다. 아이템 버프도 터지는 순간 소모되어 꺼진다.

## v69 (v68 기준) — 서버 트래픽(사용량) 급증 원인 조사 및 수정: 정적 파일 캐싱·압축 추가
- **배경**: "10명 정도가 4시간쯤 플레이했는데 Render 대역폭이 하루 8.4GB 가까이 나온다"는 제보로 조사했다. SSE(실시간 접속 목록·파티 현황) 핑/브로드캐스트는 전부 작은 텍스트뿐이라 용량에 큰 영향이 없고, 배경음악(mp3)도 페이지 한 번 열려 있는 동안은 `src/game/bgm.js`가 한 번만 내려받아 재사용하도록 이미 돼 있어서 문제가 아니었다. 인적사항 카드(프로필 사진)도 실시간으로 전체 방송되지 않고 누를 때만 따로 받아오는 구조라 문제가 아니었다.
- **진짜 원인**: 정적 파일(화면을 그리는 자바스크립트·CSS 묶음 파일, 배경음악 mp3 2종 약 5MB, 캐릭터 사진들)을 내려주는 서버 쪽 `serveStatic` 함수(`server/index.js`)가 **캐싱 헤더를 하나도 설정하지 않고 있었다** — `Cache-Control`도, `ETag`도, `Last-Modified`도 전혀 없었다. 이러면 브라우저가 "이 파일이 전과 같은지" 확인할 방법이 없어서, 새로고침·탭을 새로 열기·모바일에서 화면 꺼졌다가 다시 켜짐(백그라운드 탭 자동 새로고침) 등으로 페이지가 다시 로드될 때마다 수 MB짜리 파일들을 매번 처음부터 다시 통째로 내려받았을 가능성이 크다. 게다가 자바스크립트·CSS처럼 텍스트로 된 파일들을 압축(gzip)도 전혀 안 하고 원본 그대로 보내고 있어서, 안 그래도 큰 파일이 보통 3~4배 더 크게 나가고 있었다.
- **수정**(`server/index.js`의 `serveStatic`):
  - 빌드 결과물 중 `/assets/` 밑에 있는 파일들(자바스크립트·CSS 묶음)은 vite가 파일명 자체에 내용 해시를 넣어 만들기 때문에 — 내용이 바뀌면 파일명도 같이 바뀌므로 — `Cache-Control: public, max-age=31536000, immutable`로 **영구 캐싱**하도록 했다. 같은 파일을 다시 요청할 일 자체가 아예 없어진다.
  - 그 외 파일(`index.html`, 배경음악 mp3, 캐릭터 사진, 아이콘 등)은 매번 서버에 "바뀌었는지" 물어보되(`Cache-Control: no-cache`), 실제로 안 바뀌었으면 `ETag`/`Last-Modified`를 보고 본문 없이 `304 Not Modified`만 응답해서 재전송을 피하도록 했다.
  - `.js`·`.css`·`.html`·`.svg`·`.json`처럼 압축하면 작아지는 파일은(브라우저가 `Accept-Encoding: gzip`을 보내면) gzip으로 묶어서 보내도록 했다. mp3·png·webp처럼 이미 압축된 포맷은 다시 압축해도 거의 안 줄어서 그대로 보낸다.
  - 부수적으로, `.webp`·`.mp3` 확장자가 MIME 표에 빠져 있어서 지금까지 전부 `application/octet-stream`으로 나가고 있던 것도 `image/webp`·`audio/mpeg`로 바르게 고쳤다.
- 보스 전투 보상이 하루 3회 제한을 비껴간다는 제보는 코드상으로는 우회 경로를 찾지 못했다 — 재발하면 몇 번째 승리부터 그랬는지, 재접속/새로고침이 있었는지를 알려주면 더 조사하기로 했다.

- **문제**: 효험(토글형 영능력)이 "부적처럼 의지력이 모자라도 있는 만큼만 쓰고(0까지) 그래도 발동한다"는 부적의 규칙을 그대로 물려받고 있어서, 의지력이 0이어도 효험을 켜고 공격·부적·생존본능·원숭이 손·도깨비불에 공짜로 적용할 수 있었다(`src/game/battle.js`의 `playerTurn`·`psychicTurn`, `id === 'survival'`·`'monkey-paw'`·`'dokkaebi-fire'` 분기 전부 같은 패턴이었다).
- **수정**: 효험은 이제 의지력 10(지팡이 할인 등 보정 적용 후)을 정확히 다 낼 수 있을 때만 발동한다 — 모자라면 효험 없이 그 행동만 그대로 진행된다. 클라이언트에서도 의지력이 모자라면 효험 "켜기" 버튼 자체가 눌리지 않도록 막았고, 버튼에 필요한 의지력(예: "켜기 (의지력 10)")을 표시한다(`src/components/locations/Battle.jsx`, `src/components/locations/MultiBattle.jsx`).
- **부적은 여전히 의지력이 모자라도 쓸 수 있지만(있는 만큼만 내고 터진다), 의지력이 0일 때는 쓸 수 없게** 막았다(`playerTurn`의 `needMp` 판정에 `charm` 추가, 양쪽 전투 UI의 부적 버튼도 함께 막음). 1인 전투·다인 전투 모두 적용된다.

- **다인 전투 아군 상태변화 팝업**: 같은 편이 영능력을 쓰면 적군 영능력 발동과 똑같이 꾸며진 큰 팝업(이름 + 영능력 이름)이, 아이템을 쓰거나·전투불능이 되거나·(에너지드링크·버티기 등으로) 다시 일어서면 화면 위쪽에 짧게 뜨고 사라지는 토스트가 뜬다(`src/components/AllyPopup.jsx`의 `AllyPsychicBanner`/`AllyToastStack`, `src/game/mbattle.js`의 로그 항목에 붙는 `popup` 메타데이터, `src/components/locations/MultiBattle.jsx`에서 감지해 렌더링).

### 영능력 개선
- **설명 동기화 원칙**: 앞으로도 영능력의 실제 효과를 바꿀 때는 `PSYCHICS`(`src/game/battle.js`)의 `note`/`detail`을 같은 커밋에서 함께 고친다는 원칙을 세우고, 이번에 손댄 모든 영능력(내려쬐는 빛·형상 기억 등)에 적용했다.
- **내려쬐는 빛 = 막기 처리**: 내려쬐는 빛을 쓴 직후 들어오는 공격은 무조건 "막기"로 처리된다(피해 감소·반격 포함) — `src/game/battle.js`의 `hurt()` 맨 앞에서 `s.fallingLight` 플래그를 소비하며 강제로 `s.guard = true`로 만든다(1인 전투). 다인 전투도 `src/game/mbattle.js`의 `enemyPhase()`에서 대상이 내려쬐는 빛을 쓴 사람이면 `guard: true`로 넘긴다.
- **빌린 영능력 탭 제거**: 이미 전투 교육 삭제와 함께 지워져 있었다 — 확인만 하고 추가 조치 없음.
- **형상 기억(echo-form) 의지력 범위 고정**: 의지력 소모 공식 `(50-인내-절제+호전)`에 최소 20 · 최대 99 한도를 둬서, 극단적인 스탯 조합에서 음수나 100 이상으로 튀지 않게 했다.

## v72 (v71 기준) — Render/Supabase Egress(트래픽) 절감

실제 운영 중인 서버의 수치(초당 요청 수, 실제 전송 바이트 등)는 이 환경에서 직접 볼 수 없어 측정하지 못했다. 대신 코드를 다시 읽어보면서 "굳이 그렇게 자주 보낼 필요는 없었던" 지점들을 찾아 손댔다 — 전부 동작은 그대로이고 빈도·크기만 줄이는 저위험 수정이다. 실제 효과는 배포 뒤 아래에 새로 추가한 계측치로 확인할 수 있다.

### 계측치 추가 (관리자 전용)
- `GET /api/admin/metrics?key=<관리자키>`로 서버가 켜진 뒤 누적된 수치를 볼 수 있다: 전체 서버 스냅샷을 DB/파일에 실제로 쓴 횟수·누적 바이트(`snapshotSaveCount`/`snapshotSaveBytes`), SSE(`/api/events`) (재)접속 횟수(`sseConnectCount`), 계정 자동저장이 실제로 처리된 횟수·누적 바이트(`accountSaveCount`/`accountSaveBytes`), 평균 크기(`...Avg`), 서버가 켜진 지 몇 초인지(`upSeconds`). 서버를 재시작하면 0부터 다시 쌓인다(`server/index.js`의 `metrics`).

### 자동저장이 쉬지 않고 나가던 문제 — 가장 큰 원인을 고쳤다
- **원인**: 1초마다 도는 영력·체력 자연 회복 틱(`tickPlayer`)이 가만히 서 있기만 해도 매초 새 `player` 객체를 만들어 냈고, 그게 `src/Game.jsx`의 자동저장 트리거(`useEffect`)를 매초 다시 돌려 "저장할 것이 있다"로 계속 표시했다. 그 결과 `src/game/auth.js`의 `schedulePush`(서버로 계정 저장을 보내는 함수)가 기존엔 4초마다 거의 쉬지 않고 불렸다 — 정작 의미 있게 바뀐 건 거의 없는데도.
  - 체력·영력은 `savedAt` 기준으로 지난 시간만큼 한꺼번에 따라잡는 구조(최대 30일치까지)라서, 매초 저장하지 않아도 잃는 게 없다.
- **수정**:

### 더 손대지 않은 항목(측정·설계가 더 필요해서 보류)
아래 항목은 자료 구조를 바꾸는 작업이라, 실제 트래픽 수치를 보기 전에 섣불리 손대면 오히려 버그를 만들 위험이 있어 이번엔 넘겼다. 위 계측치로 실제 수치를 확인한 뒤, 필요하면 따로 차근차근 진행하는 게 안전하다.
- Render 자동 배포 빈도 줄이기(배포를 모아서): 이건 코드가 아니라 배포(운영) 습관의 문제라, 레포에 변경을 쌓아 두고 한 번에 배포하는 식으로 직접 조정하는 영역이다.
- DB 저장 구조를 "바뀐 데이터만 저장"하도록 테이블 자체를 쪼개는 작업: 지금도 카드(`cards.json`/`card:<id>`)·사진(`avatar:<id>:<슬롯>`)은 이미 사람별로 나눠 저장하고 있어 상당 부분은 되어 있다. 계정 본채(`account:<id>`)를 더 세분화하는 건 마이그레이션이 필요한 큰 작업이라 보류.
- 아바타 조회 빈도에 따른 캐싱 개선: 지금은 로그인/접속 시 한 번만 전체 사진을 받아오는 구조라 과도한 반복 조회는 아니지만, 더 다듬으려면 실제 조회 빈도 수치가 필요하다.

### (수정) 튜토리얼이 적 턴에서 멈추던 버그
- **원인 1**: `{ auto: 'enemy' }`/`{ auto: 'fire' }`처럼 대사 없이 자동으로만 진행되는 단계는 `lines` 필드 자체가 없었는데, `Dlg`가 `lines.map(...)`을 그대로 불러 그 단계에 들어서는 순간 렌더링이 터졌다(= 화면이 멈춘 것처럼 보임). `Dlg`의 `lines` 기본값을 `[]`로 두고, 대사가 있는 단계에서만 `Dlg`를 그리도록 바꿨다.
- **원인 2**: 적 턴·도깨비불 자동 진행 `useEffect`가 `[i, b]`에 반응하고 있어서, 그 안에서 `setB`가 일어나는 순간 같은 단계(`i`)에서 effect가 다시 돌며 `setTimeout`을 한 번 더 걸었다 — 강제해 둔 적 행동 큐를 이중으로 소비해 버리는 원인이었다. `b`/`mp`는 ref(`bRef`/`mpRef`)로 최신 값만 읽고, effect는 `[i]`에만 반응하도록 고쳤다.

### (수정) 튜토리얼 UI를 실제 전투 화면과 똑같이 바꾸고, 버튼이 안 눌리던 문제들을 고침
- **UI 전면 교체**: 바리의 대사를 보여주던 `Dlg`가 화면 바닥에 `fixed`로 떠 있는 오버레이였는데, 그 `pointer-events-auto` 패널이 실제 행동 버튼 그리드와 같은 자리를 차지해버려서 버튼이 `disabled` 상태가 아닌데도 클릭이 전혀 먹지 않는 경우가 있었다. `Dlg`를 둘로 쪼갰다 — ① `Spotlight`: 강조 링만 그리는 `fixed` + `pointer-events-none` 레이어(아무것도 가리지 않는다), ② `BariCard`: 문서 흐름 안에 들어가는 보통의 패널로, 화면 맨 위(헤더 바로 아래, 스탯 패널보다 위)에 놓여 행동 버튼과 절대 겹치지 않는다. `ScriptedBattle`과 `TutorialGroup` 둘 다 이 구조로 바꿨고, 전투 화면 레이아웃(라운드 패널 → 상대/내 스탯 패널 → 행동 버튼 그리드 → 영능력/소지품 서브패널 → 로그)도 실제 `Battle.jsx` 화면과 같은 순서로 다시 짰다.
- **패널이 저절로 닫혀서 버튼이 사라지던 문제**: `doAction`/`doPsychic`이 액션을 쓸 때마다 무조건 `setPsyOpen(false)`를 호출해서, "효험"을 켜고 "일반 공격"을 한 번 쓰기만 해도 영능력 패널이 닫혀버렸다. 그 뒤 "도깨비불을 눌러보세요" 단계가 와도 패널이 닫혀 있어 그 버튼 자체가 화면에 없었다(= "안 눌린다"로 보임). 이 무조건적인 닫기 호출을 없앴고, 대신 현재 단계의 `allow`가 `toggleBuff`/`dokkaebi-fire`/`useItem`이면 해당 패널을 강제로 열어두는 `useEffect`를 추가해 패널 상태가 항상 그 단계가 필요로 하는 대로 맞춰지게 했다. `openPsychic`/`openItems`도 토글(`!o`) 대신 항상 "열기"로 동작하도록 바꿔서, 이미 열려 있는 상태에서 다시 눌러도 닫혀버리지 않게 했다.
- **강조(스포트라이트) 보강**: 영능력 패널 안의 "효험"·"도깨비불" 버튼, 소지품 패널 안의 "사용"(피크닉) 버튼, 그리고 최상단 행동 버튼인 공격·막기·부적·간파에도 각각 `data-tutorial-*-btn` 속성을 달고, 해당하는 단계에 `highlight` 필드를 채워 넣었다. 이제 #2 영능력 튜토리얼은 "영능력 버튼 강조 → (패널이 열리면) 효험/도깨비불 버튼 강조" 순서로 짚어준다.
- **모달 배경 제거**: 전체 화면을 덮는 `fixed inset-0`+어두운 배경/블러를 걷어내고, `<section aria-label="전투">`처럼 실제 `Battle.jsx`와 똑같이 페이지 흐름 안에 그냥 들어가는 걸로 바꿨다(`ScriptedBattle`, `TutorialGroup` 둘 다). 버튼 강조용 `Spotlight`만 `fixed`+`pointer-events-none`으로 남아 있다.
- **"공격·막기 버튼이 안 눌리고 안 넘어간다" 버그**: 연습 상대(허수아비, hp 46~70)에게 플레이어의 **실제 스탯**으로 데미지를 굴리다 보니, 캐릭터가 이미 많이 성장해 있으면 "일반 공격"을 2~3번만 눌러도 허수아비가 죽어버려 `b.over`가 `'win'`이 돼버렸다. `myTurn`이 `!b.over`를 요구하기 때문에, 그 뒤로 스크립트가 요구하는 "막기"·"일반 공격" 등 단계에서 버튼이 `disabled` 상태로 영원히 잠겨 "눌러도 안 넘어간다"로 보였다. `ScriptedBattle`에 `clampAlive(state)`를 추가해, 허수아비(`ehp`)든 나(`php`)든 체력이 0 밑으로 떨어지거나 `over`가 서는 순간 체력을 각각 최대치의 35%/50%로 되돌리고 `over`를 다시 `false`로 되돌린다 — 튜토리얼 동안은 양쪽 다 쓰러지지 않는다. 이때 "~이(가) 쓰러졌다" 로그 줄도 `filterEndLog`로 함께 걸러낸다.

### #4 단체 전투 튜토리얼을 실제로 플레이 가능하게 재구현
- **기존 방식의 한계**: 처음에는 서버가 실제로 진행하는 다인 전투(네트워크로 묶인 여러 사람)를 튜토리얼 안에서 재현하기 어렵다고 보고, 대사와 "일행 구성 예시" 패널만 보여주는 설명형(`TutorialGroup`)으로 만들었었다. 하지만 다인 전투도 사실은 로컬 상태 하나(`mb` 객체)를 돌리는 `src/game/mbattle.js` 엔진이 전부 처리하고, 네트워크는 그 `mb`를 참가자끼리 동기화하는 역할만 하는 구조라, 로컬에서 "바리 + 나" 2인 파티를 직접 만들어 `mbattle.js`를 그대로 호출하면 실제 다인 전투와 동일한 로직으로 연습을 시킬 수 있다는 걸 확인하고 완전히 다시 만들었다.
- **연습 상대·헬퍼 추가(`src/game/battleTutorial2.js`)**: 2인이 같이 때려도 금방 끝나지 않을 만큼 체력을 넉넉히 둔 `TUTOR_DUMMY_GROUP`(hp 90)을 새로 추가했다. 다인 전투 생성 함수 `createMB`는 적을 `ENEMIES` 배열에서 id로 찾아오는 구조라 연습용 허수아비 객체를 바로 넣을 수 없었기 때문에, `createMB`와 동일한 필드 구성을 그대로 따르면서 적 객체를 직접 받는 `createDummyMB(enemy, rawMembers, rng)`를 새로 만들었다(내부 전용 `addLog`는 건드리지 않고, 초기 로그 한 줄은 호출하는 쪽에서 직접 넣는다).
- **새 엔진(`src/components/BattleTutorial2.jsx`의 `ScriptedGroupBattle` + `tutorialGroupSteps()`)**: `ScriptedBattle`과 같은 "단계를 순서대로 넘기는" 구조를 다인 전투 엔진(`openingInitiative`/`beginRound`/`submit`/`resolveTurn`/`useItemMB`/`afterEnemy`) 위에 그대로 올렸다. 바리(고정 스탯, agility 300으로 거의 항상 선공)와 실제 플레이어 스탯을 쓰는 "나" 2인으로 파티를 구성하고, 적의 행동은 `forcedQueue(['jab','jab','group','smash'], 20)`로 고정해 "단체 공격"(전원 동시 타격) 시연 타이밍을 정확히 맞춘다. 진행 순서: 바리가 폭죽(전원 공격력 ×2, 자신 2턴 스턴) 사용 → 내가 일반 공격 → (바리 스턴으로 자동 패스) → 내가 막기 → (바리 자동 패스) → 내가 화 올리기 → 적의 "단체 공격" 피격 시연 → 정리.
- **버그 1 — 강제 돌발 행동이 내 클릭을 가로막음**: `mbattle.js`의 `nextActor`(내부 전용)는 다음에 움직일 사람의 돌발 행동(rash)을 미리 굴려서, 플레이어가 아직 아무것도 고르기 전에 `m.act = {action:'attack', forced:true}`를 먼저 심어 둘 수 있다. 이 상태에서 "막기"를 누르면 `submit`이 `m.act`가 이미 차 있다며 `{error:'already'}`를 돌려주는데, 처음엔 이 에러를 그냥 무시하고 멈춰버려서 꼭 "버튼이 안 눌리는" 것처럼 보였다. **고침**: `bari`/`me` 모두, `submit`·`useItemMB`를 부르기 전에 `if (m?.act?.forced) m.act = null`로 미리 심어진 돌발 행동을 지우고 플레이어가 고른 행동을 그대로 받게 했다. 500회 랜덤 시뮬레이션(엔듀런스 1로 돌발 확률 최대화)으로 재현·검증, 수정 후 불일치 0건.
- **버그 2 — 아이템 사용 로그가 화면에 안 뜸**: `useItemMB`/`useItemCore`는 "바리이(가) 폭죽을(를) 터뜨렸다!" 같은 설명 로그를 자신의 리턴값이 아니라 `mb.log`에 내부적으로(`addLog`, export 안 됨) 바로 적어 넣는다. 처음엔 `resolveTurn`이 돌려주는 이벤트만 화면 로그에 올렸기 때문에, 폭죽을 썼을 때 효과(스턴+버프)는 제대로 적용되는데 그 설명 문구만 화면에서 사라지는 문제가 있었다. **고침**: `useItemMB` 호출 직전의 `mb.log.length`를 기억해 두고, 호출 직후 그 길이부터 끝까지(`mb.log.slice(before)`)를 떼어내 화면 로그에 함께 넣었다.
- **버그 3 — "단체 공격" 시연이 자주 생략됨**: 플레이어의 실제 스탯으로 데미지를 계산하다 보니 한 번의 공격·화내기로도 허수아비 체력(`mb.ehp`)이 그 라운드 안에 0 밑으로 떨어지는 경우가 많았는데, `resolveTurn`은 `ehp`가 0 이하가 되는 걸 확인하면 **그 즉시 `mb.over='win'`을 세우고 리턴**해 버려서, 그 라운드의 적 턴(`enemyPhase`) 자체가 통째로 건너뛰어졌다 — 하필 "단체 공격" 큐가 걸려 있던 적 턴이 사라지는 바람에 시연이 자주 생략됐다. 전투가 끝난 "뒤에" 체력을 복구하는 기존 방식(`clampMB`)은 이미 건너뛴 턴을 되돌릴 수 없어 효과가 없었다. **고침**: 매 `resolveTurn` 호출 **직전에** `mb.ehp = Math.max(mb.ehp, 999_999)`로 미리 끌어올려 두는 `preserveEnemyHp(mb)`를 추가해, 해당 라운드 안에서는 절대 0 이하로 떨어지지 않게 막았다(화면에 보여줄 체력은 `resolveTurn` 뒤 `clampMB`가 다시 최대치의 35%로 정리한다). esbuild로 실제 모듈을 번들링해 Node.js에서 직접 돌리는 방식(React/브라우저 없이)으로 1000회 랜덤 시뮬레이션을 돌려 `단체 공격 시연 1000/1000, 크래시 0, 돌발행동 불일치 0`으로 확인했다.
- **허브 선택 화면도 팝업에서 인라인으로**: `BattleTutorialHub`의 "어떤 걸 연습할지 고르는" 첫 화면도 `fixed inset-0`+어두운 배경의 모달이었는데, 이를 실제 적 선택 화면(`Battle.jsx`의 `ENEMIES` 그리드)과 같은 느낌의 `ink-panel` 카드 그리드로 바꿔 `<section>` 안에 그대로 들어가게 했다. `src/components/locations/Battle.jsx`도 `tutorialOpen`이 참이면(`phase === 'pick' && tutorialOpen`) 적 목록·"전투 안내" 버튼·슬로우파이트 패널 등을 전부 숨기고 `BattleTutorialHub`만 화면 전체를 차지하도록 일찍 리턴하게 고쳤다 — 이제 "전투 안내"를 누르면 다른 전투를 고를 때처럼 팝업 없이 화면이 그대로 바뀐다.

### 튜토리얼 대사가 멋대로 넘어가던 문제 — 모든 대사는 '다음'을 눌러야만 넘어가게
- **원인**: `auto: 'start'|'enemy'|'fire'|'bari'`처럼 전투 진행 자체를 자동으로 처리하는 단계들이, 대사(`lines`)가 있든 없든 상관없이 작업이 끝나면 곧장 `setTimeout(next, ...)`으로 다음 단계로 넘어가 버렸다. 특히 대사와 `auto`가 함께 붙은 단계(예: "직접 싸워 볼까요?"+`auto:'start'`, 또는 #4의 "저는 폭죽을 사용해볼게요"+`auto:'bari', bariItem:'firecracker'`)는 텍스트가 뜨자마자(50~700ms 만에) 다음 줄로 넘어가 버려서 읽을 시간이 없었다 — `BariCard`의 '다음' 버튼이 `hideNext={!!step.allow || !!step.auto}` 조건으로 애초에 숨겨져 있어, 사용자가 개입할 방법 자체가 없었다.
- **고침**: 두 군데 공통 규칙으로 정리했다 — ① `BariCard`를 렌더링할 때 `hideNext`를 `!!step.allow`로만 판단하게 바꿔서(`!!step.auto` 조건 제거), 대사가 있는 단계는 `auto`가 섞여 있어도 항상 '다음' 버튼이 뜬다(실제 행동 버튼을 눌러야 넘어가는 `allow` 단계만 '다음' 버튼이 숨는다, 그건 원래 의도대로다). ② `auto: 'start'/'enemy'/'fire'/'bari'`를 처리하는 다섯 개의 `useEffect`(`ScriptedBattle`에 3개, `ScriptedGroupBattle`에 2개) 전부, 전투 처리(배틀 생성·적 턴·도깨비불·바리 턴)는 그대로 즉시 수행하되, 그 끝에 있던 `next()` 호출을 `if (!step.lines?.length) next()`로 바꿔서, 대사가 있는 단계는 자동으로 넘어가지 않고 사용자가 '다음'을 눌러야만 다음 단계(index)로 넘어가게 했다. 대사가 아예 없는 순수 진행용 단계(`{ auto: 'enemy' }` 등)는 기존처럼 자동으로 계속 흘러간다.

### #3 '내 소지품 확인하기' 안내 — 가짜 버튼 대신 진짜 사이드바 버튼을 직접 누르게
- **문제**: #3 튜토리얼의 첫 안내("실제 화면에는 '내 소지품 확인하기' 버튼이 있어요. 연습을 위해 여기에도 똑같은 버튼을 뒀어요")가 가리키는 `allow: 'openItems'` 단계는, 이 시점엔 아직 전투가 시작되지 않아(`b`가 `null`) 애초에 행동 버튼 그리드 자체가 렌더링되지 않는 상태였다 — 즉 "똑같이 둔 버튼"이 실제로는 화면에 없어서, 사용자가 누를 버튼이 안 보이는 것처럼 느껴질 수 있었다.
- **고침**: 가짜 버튼을 흉내 내는 대신, 실제 사이드바(`ProfileSidebar.jsx`)의 '내 소지품 확인하기' 버튼에 `data-tutorial-real-items-btn` 속성을 달아 두고, 해당 단계의 `allow`를 `'realItems'`로 바꿨다. `ScriptedBattle`에는 `step.allow === 'realItems'`일 때만 활성화되는 `document.addEventListener('click', ..., true)` 리스너를 새로 추가해, `[data-tutorial-real-items-btn]`을 직접 클릭하면(캡처 단계라 다른 핸들러보다 먼저 감지) 다음 단계로 넘어가게 했다. 이 버튼은 `BattleTutorial2.jsx` 바깥(`ProfileSidebar`)에 있어서 평소처럼 `onOpenItems`도 그대로 호출되므로, 클릭하면 실제 소지품 화면이 정말로 열린다 — 튜토리얼 안에 똑같이 생긴 걸 하나 더 만드는 대신 진짜 화면을 그대로 보여주는 식으로 바꾼 것. 강조(`Spotlight`)도 같은 selector를 그대로 써서 실제 버튼을 짚어 준다.

### #4 단체 전투 튜토리얼에 바리의 '도깨비불' 시연 추가
- **추가**: 기존엔 #4에서 바리가 폭죽(아이템)만 보여줬는데, 바리의 고유 영능력인 '도깨비불'도 실제로 쓰는 과정을 보여주도록 `tutorialGroupSteps()`에 라운드 4개를 더 이어 붙였다 — 부적 시연(라운드3) 직후, 바리가 `{ action: 'psychic', psychic: 'dokkaebi-fire' }`로 도깨비불을 쓰고(라운드4), 2턴 동안 기를 모으는 동안(라운드5·6) 당신은 공격·막기를 계속하고, 마지막 라운드(7)에서 터뜨린다. 바리의 고정 스탯(의지력 100)이라 의지력 20 소모는 문제가 되지 않는다.
- **아군 영능력 팝업 재사용**: 실제 다인 전투(`MultiBattle.jsx`)에서 아군이 영능력을 쓰면 적 비기와 같은 느낌의 큰 배너(`AllyPsychicBanner`, `src/components/AllyPopup.jsx`)가 뜬다 — `resolveTurn`이 영능력을 쓴 턴의 첫 이벤트에 `popup: { type: 'psychic', name, psychic }`를 달아 두고, 그걸 보고 띄우는 방식이다. `ScriptedGroupBattle`에도 똑같은 컴포넌트를 그대로 가져와(`import { AllyPsychicBanner } from './AllyPopup'`) `allyBanner` state와 6.2초 뒤 자동으로 꺼지는 `useEffect`를 추가하고, 바리의 자동 턴(`auto: 'bari'`) 처리 안에서 `resolveTurn`이 돌려준 이벤트 중 `popup?.type === 'psychic'`인 것을 찾아(`announceAllyPsychic`) `PSYCHICS`(`src/game/battle.js`)에서 라벨·설명을 찾아 띄운다. 도깨비불을 "쓰는" 라운드(캐스트)에서만 이 이벤트가 나오고, 이어지는 충전 라운드에는 나오지 않는다 — 실제 게임과 동일하다(500회 시뮬레이션으로 확인: 캐스트 500/500에서 팝업 발생, 충전 라운드에서는 0건).
- **버그 발견 — 상대 체력이 999,xxx처럼 비정상적으로 표시될 수 있었음**: 이전에 추가한 `preserveEnemyHp(mb)`(매 `resolveTurn` 호출 직전 `mb.ehp`를 999,999까지 끌어올려 두는 안전장치, "단체 공격" 시연이 생략되지 않게 하기 위한 것)가 *모든* 바리/나의 턴마다 호출되는데, `clampMB`는 그동안 `mb.ehp <= 0 || mb.over`일 때만 되돌리고 있었다. 즉 한 번이라도 공격이 오간 뒤에는 `mb.ehp`가 999,999에서 데미지만큼만 깎인 거대한 값으로 계속 남아, 화면에 "999,850 / 90"처럼 보이는 문제가 숨어 있었다(도깨비불 폭발처럼 큰 피해가 아니어도 첫 공격부터 바로 발생). **고침**: `clampMB`의 조건에 `mb.ehp > mb.enemy.hp`(= 비정상적으로 큰 값)도 추가해서, 매 턴 처리 뒤 체력을 항상 최대치의 35%로 안전하게 되돌리도록 했다. 500회 시뮬레이션으로 모든 턴 뒤 `ehp`가 `0 < ehp <= enemy.hp` 범위 안에 있는지 확인(`overflowAfterClamp`), 전부 0건.

### 튜토리얼 완주 보상 — 무구를 이름만 보고 고르지 않고, 효과를 직접 보고 고르게
- **문제**: `BattleTutorialHub`에서 네 튜토리얼을 다 마치면 뜨는 보상 선택 화면이, `WEAPONS` 10종의 이름만 버튼으로 나열해 둔 목록이었다 — 무슨 효과가 있는지 전혀 안 보여주고 이름만 보고 고르게 되어 있었다.
- **고침**: 뒷산 > 무구보관소(`Armory.jsx`)의 "탭처럼 고르고 아래에 설명이 뜨는" 패턴을 그대로 가져왔다. 무구 10종을 `role="tablist"` 알약 버튼 줄로 늘어놓고(`selWeapon` state, 기본값은 첫 번째 무구), 하나를 누르면 그 아래 패널에 해당 무구의 `desc`(배경 설명)와 `effectText`(실제 효과, 전투 패널 전체에서 쓰는 것과 동일한 문구)가 뜬다. 그 패널 안에 "○○ 받기" 버튼을 둬서, 효과를 확인한 뒤 바로 그 자리에서 받아갈 수 있게 했다(기존의 "이름만 누르면 즉시 확정"이던 방식 대신, 미리보기 → 확정의 두 단계로 바뀌었다).

### 튜토리얼 중엔 사이드바의 체력·의지력도 100/100으로
- **문제**: 튜토리얼이 모달이던 시절엔 전체 화면을 덮는 어두운 배경 때문에 몰랐는데, 인라인으로 바뀌면서 왼쪽(모바일은 상단) `ProfileSidebar`가 튜토리얼 화면과 함께 그대로 보이게 됐다. `ProfileSidebar`는 항상 실제 `player.hp`/`player.mp`를 그려 주는데(`VBar`), 연습 전투 패널 안의 체력·의지력은 100으로 고정해 두었지만 사이드바 쪽은 그대로 실제 수치를 보여주고 있어서 "100으로 시작한다"는 원래 의도와 어긋나 보였다.
- **고침**: `Battle.jsx`의 `tutorialOpen` state가 바뀔 때마다 그 값을 그대로 상위에 알려주는 콜백 prop `onTutorialActive`를 새로 추가했다(`useEffect(() => { onTutorialActive?.(tutorialOpen); return () => onTutorialActive?.(false) }, [tutorialOpen])` — 언마운트되거나 화면을 벗어날 때도 반드시 꺼서, 다른 화면에 가서까지 100으로 고정된 채 남지 않게 했다). `Gym.jsx`는 `{...rest}`로 그대로 전달하므로 손댈 필요가 없었다. `Game.jsx`에 `tutorialStatsPreview` state를 두고 `<Gym onTutorialActive={setTutorialStatsPreview} .../>`로 연결한 뒤, `<ProfileSidebar>`에 넘기는 `player`를 `tutorialStatsPreview`가 참일 때만 `{ ...player, hp: 100, hpMax: 100, mp: 100, mpMax: 100 }`로 바꿔치기해서 넘긴다 — 실제 `player` 객체나 저장되는 값은 전혀 건드리지 않고, 화면에 "보여주는" 값만 바뀌므로 튜토리얼을 닫는 즉시 원래 수치로 돌아온다.
